# 技术风险

第一期的风险主要在数据源和计算口径，不在下单速度。这些问题要在跑通 Elysium 时一并设计进去，而不是等上线后再补。第一期的主要风险是自建窗口和 RPC，而不是官方索引密钥。

| 可能出现的问题 | 为什么会发生 | 怎么防 |
| --- | --- | --- |
| 官方索引限流、要密钥，或突然停更 | 公开 Graph 节点不稳定，生产通常要自己的 API 密钥；子图版本也会换 | 接入层把端点做成可配置，主备切换；每个数字标明来源和时间；索引挂了要明确报错，不能拿过期表冒充新数据 |
| 1 小时档并不实时 | 官方小时档最多可能落后将近一个小时，当前这一小时往往还不完整 | 界面标明数据截止时间；当前未结束的小时要标成未完成，或只用已完成的小时去比上一窗口 |
| USD 计价失真 | 冷门代币的 volumeUSD、tvlUSD 可能被错误价格放大，APR 会虚高 | 与 TVL、成交量门槛一起看；异常高 APR 要能对照链上原始数量，必要时降级为「计价存疑」 |
| 池子太多，一次拉不完 | 官方查询通常每页最多 1000 条，BSC 上工厂池会远超这个数 | 分页拉全清单，再按门槛预筛；不要把全历史 swap 都存下来，只存分档汇总 |
| 金额算错、精度丢失 | JavaScript 普通数字只有约 15 位有效精度，链上数量不能直接用它乘除 | 数量和价格全程用大整数或十进制库，只在展示时再四舍五入 |
| fees APR 算高或算错 | 动态费已经很普遍，部分 Uniswap 池还抽协议费；用费率档乘成交量会偏掉 | 只用窗口内实际归 LP 的手续费年化；看板上标 hook 类型，特殊 hook 池不按普通仓推荐 |
| 和上一窗口对比对不齐 | 时区、未结束的小时、缺档会对不齐「这一小时 vs 上一小时」 | 第一期按自建窗口的起始时间对齐；以后有官方档时按官方 `periodStartUnix` 对齐。缺档就显示为空，不要用别的小时凑 |
| Pancake 与 Uniswap 图式不完全一样 | 两套官方索引字段和部署地址可能有小差异 | 差异关在适配器里，统一模型保持同一套字段。Infinity 与 Uniswap V4 结构不同，必须分开写；BSC 上这两套暂时没有 Labs 官方生产索引，按自建或标明非官方的社区索引来接 |
| Elysium 作为第一条会更重 | 没有官方预汇总，只能从日志自建窗口，RPC 有查询范围限制，还会有重组 | 这是第一期必须扛住的成本，不能改回先跑有官方索引的链来回避。适配器对齐官方地址和 SDK；已定窗口必须自建并如实展示，不得空着，也不得用其他窗口冒充。生产验收用带归档的节点，读状态优先用 StateView；不把全历史原始成交长期全留。联调可用官方公开节点，但须标明临时公开源（public_temporary） |
