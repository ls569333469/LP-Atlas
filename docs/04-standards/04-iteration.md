# 更新与迭代

迭代的第一要求是：先改标准，再改代码和 `docs/`。禁止先改实现再回头改标准，也禁止以「顺手优化」改已定口径、目录、默认策略或 API。

1. 每一期必须先达到项目标准里的验收条款，才能开始下一期。第一期的门是「跑通 Elysium Uniswap V3 与 V4」。
2. 改已确定事项、数据口径、API 形状、默认策略或目录切分，属于破坏性变更：必须先写入变更说明（改了什么、为什么、依据），用户确认后再改标准与代码。
3. 官方协议或 SDK 变更时，先对照标准标出差异，确认后再改；SDK 升级单独提交，并重跑口径测试。
4. 一次迭代只做一件事。不得在修 bug 或接新协议时顺带换框架、改目录或重写无关模块。
5. 存储结构变更必须带迁移；API 破坏性变更必须升主版本（`/api/v2`），旧版本的下线时间要写进变更说明。
6. 产品版本采用主、次、修订号：不兼容的口径或 API 改动主版本，新功能改次版本，修补改修订号。每次发布写明变更说明，并对照当前阶段的验收标准。
7. 新功能先判断是热路径还是旁路，故障时怎么降级，会不会打破第一期边界。暂缓项（Fee 对 IL 列、提醒、自动开仓）未解禁前不得做进实现。钱包与开仓的设计必须先写进标准；实现须等扫描验收通过，不得提前写进产品代码。
8. 每次迭代结束时，更新项目标准中的交接表与 `docs/`：当前阶段、最近变更、下一步只做什么、明确不要做什么。
9. 进度与审计以 `docs/04-standards/05-roadmap.md` 和项目标准中的「更新迭代计划」为准。完成须有证据才打钩；每次迭代结束同步更新该计划与交接表。
